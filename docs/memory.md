# Memory

The agent remembers across conversations. Memory has two layers, both persisted
in the embedded database, and each serves a different purpose.

## Two layers

### 1. Curated memory (always in context)

A single markdown document the agent maintains itself — the same **Memory**
document described in **[The agent's identity](agent-identity.md)**. It's always
present in the system prompt, so recall is instant and free of any search step.
This is where the agent keeps the things it has decided are worth holding onto
permanently: important decisions, known issues, durable facts about your
environment, recurring patterns.

It's deliberately bounded. The agent prunes and rewrites it rather than letting
it grow without limit — think of it as the agent's working notes, not its
archive.

### 2. Searchable memory (recalled on demand)

An embedding-indexed store for everything else. The agent writes entries here as
it works, and queries them **by meaning** — not keyword — when something becomes
relevant. This is the archive: far larger than what could fit in the prompt, and
retrieved only when needed.

- **Embeddings** are generated by the configured embedding platform — Amazon
  Titan v2 on Bedrock by default; see
  [Memory embeddings](configuration.md#memory-embeddings) — and stored
  alongside each entry. With embeddings off (`EMBEDDING_PROVIDER=none`),
  entries still persist and recent ones still open a new conversation, but
  search by meaning returns nothing.
- **Search** runs as vector similarity over the embedded SQLite database
  (using `sqlite-vec`), ranked by semantic closeness. Every message you send is
  searched automatically over a recency window, so the agent starts each turn
  holding whatever that message matched; it can also search all of its memory
  itself when a task needs more.
- **A new conversation picks up where the last one stopped.** It opens with the
  entries the agent recorded in the last four hours, newest first, up to a few.
  This works on every surface, voice chat and meetings included, and the entries
  are not shown in the conversation. A new channel thread or call where other
  people are present opens with these entries too, so the agent can mention there
  what it recorded in a private conversation. For anything older, ask the agent
  to search its memory, or to keep the fact in its curated memory.
- Each entry has a **category** (observation, action, decision, or event) and an
  **importance** score, so recall can be scoped and weighted.
- **A high enough importance keeps an entry always in view.** Those entries are in
  front of the agent on every turn, whatever the conversation is about — the same
  standing as the curated document. Everything below that score is retrieved only when
  a message matches it. Score sparingly: an always-in-view entry is paid for on every
  turn of every conversation, while the rest cost nothing until they are relevant.
- That set is **bounded** — the highest-scored entries up to a fixed size. Past the
  bound an entry is not dropped: it goes back to being retrieved when a message matches
  it, or when the agent searches for it. So marking everything important marks nothing
  in particular.

## How the agent uses it

You don't manage memory directly — the agent does, through three
[tools](tools.md#memory):

- **Write** — record something worth keeping (with a category and importance).
  The embedding is computed in the background, so writes don't slow the
  conversation.
- **Search** — pull back past entries by meaning, or the newest ones. A search
  can be limited to a category and a time window, such as last Tuesday, and
  ordered by relevance or newest first.
- **Delete** — remove entries that are no longer accurate.

In practice this is invisible: you tell the agent something, and it decides
whether to fold it into curated memory, drop it into searchable memory, or both.
Later, in an unrelated conversation, it can search and recall it. What it did not
record, it can still find in the conversation where it was said, with its
[conversation search](tools.md#conversation-search).

## Telling the agent to remember

Just say so. "Remember that we deploy on Fridays," "make a note that the billing
service owner is Dana," "forget what I said about the old API key" — the agent
maps these to the right memory operations. If you want something kept *always in
view*, ask it to add the fact to its curated memory specifically; for everything
else, the searchable store is the default.

## Persistence and backup

Both layers live in the agent's SQLite database, so they survive restarts,
daily session resets, and upgrades. Memory is included
in the `.prism` export from the **[Web UI](web-ui.md#profile)**, so backing up
the agent backs up everything it remembers.
